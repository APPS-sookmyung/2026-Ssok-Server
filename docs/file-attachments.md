# 로컬 파일 저장·첨부 API

## 이번 구현 범위

- 로컬 비공개 저장소를 사용합니다. S3·AWS SDK·외부 파일 업로드는 추가하지 않았습니다.
- PDF·PNG·JPEG를 파일당 최대 10 MiB(10,485,760바이트)까지 허용합니다.
- 확장자와 실제 바이트 시그니처를 확인하고, 클라이언트의 MIME 값을 신뢰하지 않습니다.
  문서·이미지 내용 전체 분석이나 악성코드 검사는 이번 범위에 포함하지 않습니다.
- 원본 이름의 경로는 제거하며, 파일은 UUID 이름으로 저장합니다. 같은 파일명도 별개로 보관합니다.
- 파일 저장 경로·저장 키를 API에 노출하지 않고, static resource로 공개하지 않습니다.

## 용도 및 권한

| 용도 | 업로드 | 조회·다운로드 | 삭제 | 라이브러리·북마크 |
|---|---|---|---|---|
| BOOKMARK | OWNER·EDITOR | 해당 공간의 OWNER·EDITOR·VIEWER | OWNER·EDITOR, 다른 저장자의 자료도 가능 | 북마크 생성, 같은 공간의 폴더 선택 가능 |
| CHAT_ATTACHMENT | OWNER·EDITOR | 업로더 본인 + 현재 검색·대화 가능 역할 | 업로더 본인 + 현재 쓰기 가능 역할 | 북마크 생성 안 함, 폴더 지정 불가 |

대화 첨부는 아직 대화방·메시지에 연결하지 않습니다. 공개 범위도 업로더 본인으로 제한합니다.
실제 대화 API가 구현되면 소유권·대화방 권한·첨부 수명 정책을 별도로 연결해야 합니다.
팀에서 제거되거나 역할이 VIEWER로 바뀌면 대화 첨부 접근도 즉시 차단됩니다.
북마크 파일은 VIEWER도 다운로드할 수 있습니다. 공간 소유자는 공간 전체 삭제를 통해 첨부도 정리할 수 있습니다.

## API

모든 API는 Authorization: Bearer accessToken 인증이 필요합니다.

| 기능 | 요청 | 성공 |
|---|---|---|
| 업로드 | POST /api/files, multipart/form-data | 201, FileResponse |
| 메타데이터 | GET /api/files/{fileId} | 200, FileResponse |
| 다운로드 | GET /api/files/{fileId}/download | 200, 원본 바이트 |
| 삭제 | DELETE /api/files/{fileId} | 200, true |

업로드 필드:

- file: 파일 파트, 필수
- spaceId: 소속 스페이스 ID, 필수
- purpose: BOOKMARK(기본) 또는 CHAT_ATTACHMENT
- libraryId: BOOKMARK인 경우만 선택 가능. 다른 공간의 폴더는 404

FileResponse: fileId, spaceId, bookmarkId, libraryId, uploaderId, purpose,
originalName, contentType, sizeBytes, createdAt, downloadUrl.
downloadUrl은 인증이 필요한 백엔드 상대 주소이며 공개 URL이 아닙니다.
다운로드 응답은 attachment, no-store, nosniff 헤더를 사용합니다.

오류: 인증 없음 401, 권한 없음 403, 공간·파일·폴더 없음 404,
잘못된 요청·빈 파일 400, 용량 초과 413, 허용하지 않은 형식 415, 저장소 장애·파일 불일치 503.

## 북마크와 AI

- 기존 URL 저장 API는 유지됩니다. 일반 링크는 type=LINK입니다.
- 파일은 type=FILE이고, 목록·상세에 fileId가 추가됩니다. url은 인증 다운로드 경로입니다.
- 파일 북마크는 analysisStatus=NOT_SUPPORTED입니다. 처리 중·분석 실패로 표시하지 않습니다.
- 파일 업로드 시 AI 분석 이벤트를 발행하지 않으며, 재분석·추천 요청도 400으로 거절합니다.
- 라이브러리 삭제·같은 공간 안의 이동은 원본 파일과 북마크를 유지합니다.
- 파일 북마크를 삭제하면 메타데이터와 실제 파일을 함께 정리합니다.

프론트파트와 FILE 카드·다운로드·업로드 진행 및 오류 표시를 연결해야 합니다.
AI파트와 PDF·이미지 분석/검색 지원·인증된 파일 전달 규격을 결정한 후 별도 연동해야 합니다.

## 로컬 실행 설정

기본 경로는 실행 디렉터리 기준 .data/files입니다. Git에서 제외됩니다.

```properties
FILE_STORAGE_LOCAL_ROOT=C:/ssok-private-files
```

해당 디렉터리는 서버 프로세스가 읽고 쓸 수 있어야 하며 웹서버의 공개 정적 경로에 두지 않습니다.
로컬 실행에는 AWS 계정·자격 증명이 필요하지 않습니다.
파일 저장소는 ObjectStorage 인터페이스로 분리했습니다. S3 도입은 팀 회의 후 별도 구현합니다.
S3로 옮길 때에는 기존 파일·저장소 식별자·삭제 작업도 함께 이전해야 합니다.

## 트랜잭션과 파일 정리

- 물리 파일은 DB와 함께 원자적으로 커밋할 수 없으므로 file_deletion_jobs에 정리 작업을 남깁니다.
- 업로드 전에 별도 트랜잭션으로 정리 의도를 기록합니다. 업로드 성공 시 메타데이터와 함께 의도를 제거합니다.
- 업로드 트랜잭션이 롤백되거나 프로세스가 종료되면 남은 파일은 1시간 후 정리 대상이 됩니다.
- 파일·북마크·스페이스 삭제는 같은 DB 트랜잭션에서 정리 작업을 기록하고 메타데이터를 제거합니다.
- DB 커밋 후 실제 삭제를 시도합니다. 실패하면 재시도 횟수와 다음 시간을 갱신해 다시 처리합니다.
- 기본 정리 주기는 60초, 한 번에 최대 50건입니다. 실패 간격은 증가하며 최대 1시간입니다.
- DB 롤백 시에는 정상 파일을 삭제하지 않습니다. 다른 저장소 식별자의 작업은 실행하지 않습니다.
- file.cleanup.enabled=false는 정기 재시도만 끕니다. 커밋 후 즉시 정리는 유지됩니다.

## DB 적용 및 회의 안건

scripts/mysql/20261123_file_attachments.sql은 기존 링크를 유지하며 파일 테이블·정리 작업 테이블과
북마크 type, NOT_SUPPORTED 분석 상태를 추가합니다. 백업 후 새 앱 시작 전에 적용합니다.
이번 작업에서 기존 개발·운영 DB에는 적용하지 않습니다.

회의에서 S3 등 운영 저장소·권한과 비용 담당, 파일 백업·보존 기간, 대화 첨부 수명,
AI 지원 범위를 확정해야 합니다. 로컬 파일 운영 시 서버 재배포와 별개로 보존되는 경로가 필요합니다.

## 검증 결과 (2026-11-23)

- MySQL 8.4.11 전용 DB와 임시 로컬 디렉터리에서 전체 122개 테스트 통과, bootJar 빌드 성공.
- PDF·PNG·JPEG 업로드와 바이트 일치 다운로드, JWT 접근·역할·비멤버·개인 첨부 권한을 검증했습니다.
- 파일·북마크·스페이스 삭제 후 물리 파일 제거, 폴더 삭제 시 파일 유지, 실패 후 재시도와 업로드 롤백 복구를 검증했습니다.
- 성공한 업로드의 임시 정리 작업이 같은 DB 커밋에서 제거되는 회귀 테스트를 통과했습니다.
- 별도 스키마 DB에서 마이그레이션 재실행·기존 LINK 데이터 보존·FILE 데이터 저장을 검증했습니다.
- AWS·실제 AI 서버·프론트 연결은 수행하지 않았고, 기존 개발·운영 DB에는 적용하지 않았습니다.
