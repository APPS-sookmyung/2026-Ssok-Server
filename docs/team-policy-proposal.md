# 기능 정책 및 API 협의안

사용자가 제공한 기능 명세와 현재 코드 기준입니다. 아래 제안은 팀 합의 완료를 의미하지 않습니다.

## 확정된 역할 정책

- OWNER: 스페이스 관리, 초대·제거·역할 변경, 자료 조회·작성·삭제·검색·AI 사용.
- EDITOR: 같은 팀의 다른 저장자 자료도 수정·삭제 가능. 관리 기능은 불가.
- VIEWER: 참여 공간과 자료의 목록·상세만 조회. 검색·대화·댓글 작성·자료 변경 불가.
- 역할은 스페이스별로 적용하며, 서버가 인증 사용자와 실제 자료 소속을 검증합니다.
- OWNER로 바꾸는 일반 역할 변경 요청은 불가합니다. 소유권 이전은 별도 기능입니다.

## 4번 팀원 관리 정책 — 사용자 확정

- EDITOR·VIEWER는 팀을 직접 탈퇴할 수 있습니다. 저장한 팀 자료는 남깁니다.
- OWNER는 기존 팀원에게 소유권을 이전한 뒤 탈퇴합니다. 마지막 OWNER의 직접 탈퇴는 차단합니다.
- 이전받는 대상은 같은 팀의 EDITOR 또는 VIEWER이고, 이전 OWNER는 EDITOR가 됩니다.
- 개인 스페이스는 탈퇴·소유권 이전을 허용하지 않습니다. 소유자의 스페이스 삭제는 허용합니다.
- 소유자 필드와 양쪽 멤버 역할은 한 트랜잭션에서 변경합니다.
- 탈퇴·제거·역할 변경·소유권 이전은 같은 공간에 대한 동시 변경을 직렬화해야 합니다.

구현 API:

| 기능 | 요청 | 성공 응답 |
|---|---|---|
| 자기 탈퇴 | DELETE /api/spaces/{spaceId}/members/me | 200, 기존 공통 응답 및 true |
| 소유권 이전 | PATCH /api/spaces/{spaceId}/owner, body: {"memberId": 123} | 200, 신규 OWNER MemberDto |

비로그인 401, 비멤버·비소유자·개인 공간 요청 403, 다른 공간 또는 없는 대상 404,
자기 자신에게 이전하거나 잘못된 memberId를 보내는 요청은 400입니다. memberId는 멤버십 ID입니다.

## 2번에서 팀과 확정할 항목

| 항목 | 제안 | 협업 및 결정할 내용 |
|---|---|---|
| 라이브러리 구조 | 사용자 확정: 공간 바로 아래 1단계, 북마크는 라이브러리 0~1개에 선택적으로 소속 | 프론트·북마크 담당자와 libraryId 요청·응답 연결 |
| 라이브러리 삭제 | 사용자 확정: 북마크는 공간에 남기고 라이브러리 연결만 해제 | 프론트와 삭제 안내·미분류 표시 연결 |
| 초대 | OWNER가 발급, 로그인 및 수락 뒤 멤버십 생성, 기본 EDITOR | 프론트와 수락·만료·취소 화면, 백엔드와 이메일 지정·만료 시간·토큰 보관 방식을 결정 |
| 초대 링크 | 취소·만료 가능한 토큰, 링크를 여는 동작만으로 가입하지 않음 | 프론트와 URL, 백엔드와 재사용·사용 횟수·발급 시 역할을 결정 |
| 자료 공유 | 우선 원본 공간의 접근 권한을 요구하는 링크 | 프론트·북마크 담당자와 외부 공개 필요 여부를 결정. 공개는 별도 보안 모델 필요 |
| 검색·AI | Spring이 OWNER·EDITOR 공간만 전달, AI는 범위 내 검색 | AI 담당자와 분석·콜백·대화 요청 ID·인증·삭제·실패 처리 규격을 결정 |
| 파일 | 저장소 키로 보관하고 다운로드 때 공간 권한 확인 | 프론트·AI 담당자와 종류·용량·지원 분석·URL 전달 방식을 결정 |
| 신규 기능 담당 | 사용자: 팀원·초대·라이브러리·파일·알림·계정 | 다른 백엔드 담당자와 북마크·분석·검색·대화 및 이벤트 연결 책임을 확정 |

수락형 초대의 현재 API와 SMTP 설정은 docs/space-invitations.md를 참고합니다.

## 완료 기준

- 프론트·AI·다른 백엔드 담당자가 위 미정 정책과 API 필드·오류 코드를 확인합니다.
- 결정된 내용으로 이 문서 및 API 명세를 갱신하고, 담당과 구현 순서를 지정합니다.
- 신규 API에서 공통 권한 검사를 재사용하고 권한·소속·삭제 후 접근을 테스트합니다.
